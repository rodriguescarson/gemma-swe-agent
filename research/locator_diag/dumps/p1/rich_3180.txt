## Description

Update wrapping logic to fix issues with CJK charcters disappearing when the "fold" location sat *within* a double-width character. Ensure we retain browser logic of: 


> if there is no space on the current line, move to a new line, and if theres not enough space on the entire new line, fold the text over multiple lines at appropriate locations.

Adds some additional tests and docstrings, documentation etc.

Fixes #3176 

The wrapping process is overall still quite simple and doesn't match the browser in many cases. For example, wrapping does not consider punctuation (lines can begin with punctuation), and whitespace is handled differently (but practically speaking it seems sensible).

FILES: rich/cells.py:124-144 (chop_cells)
CAUSE: In `chop_cells`, if a single character's cell size exceeds `max_size`, it's still added to a new line but the resulting string might be empty or truncated depending on how it's used, and more importantly, it doesn't handle cases where `max_size` is smaller than any available character cell size, potentially causing characters to "disappear" or be replaced by whitespace if the wrapping logic expects at least one cell. Actually, looking at `chop_cells`, it uses `reversed(characters)` and appends, which should keep the character. However, the issue says "disappearing when the 'fold' location sat *within* a double-width character". If `max_size` is 1 and a char is width 2, it starts a new line with that char, but then the next `max_size` check might be off. The reproduction showed that `Text("あ").wrap(console, 1, overflow="fold")` resulted in `Lines([<text ' ' []>])`, which is definitely disappearing/replacing.

Wait, if `Text("あ")` (width 2) is wrapped with width 1, `chop_cells("あ", 1, 0)`:
`characters = [("あ", 2)]`
`total_size = 0`
`lines = [[]]`
Loop: `character="あ", size=2`. `0 + 2 > 1` is True.
`lines.append(["あ"])` -> `lines = [[], ["あ"]]`
`total_size = 2`
Returns `["", "あ"]`.
Then `Text.wrap` does `line.truncate(width, overflow=wrap_overflow)`. If `wrap_overflow` is "fold", it doesn't truncate. But `line.rstrip_end(width)` is called. 

The bug is likely that `chop_cells` can return empty strings at the beginning or end, and the wrapping logic in `rich/text.py` or `rich/_wrap.py` might be miscalculating positions when `chop_cells` is involved. Specifically, `divide_line` in `rich/_wrap.py` doesn't seem to handle the return values of `chop_cells` perfectly when `start` indices are involved.
