## Problem

- The issue is a maintainer PR: "fix infinite loop in append / Fixes https://github.com/Textualize/rich/issues/3479". That is the whole text.
- Bug: `Text.append(text)` and `Text.append_text(text)` extend `self._spans` from a generator over `text._spans`.
  - When `text is self` and it has spans (any style), the generator reads the list it is appending to.
  - The list never ends, and memory grows without bound.
- Gold: `rich/text.py`, 2 hunks, +2/-2. It iterates `text._spans.copy()` at both identical sites (`append` and `append_text`).
- FAIL_TO_PASS (1): `tests/test_text.py::test_append_loop_regression`. It asserts:
  - `a = Text("one", "blue"); a.append(a)` gives `a.plain == "oneone"`;
  - `b.append_text(b)` gives `"twotwo"`.
  - Self-append must **work**, not raise, at **both** sites.
- PASS_TO_PASS: 108 tests in `tests/test_text.py`.

## Root cause

- **Taxonomy: HANG_INFINITE_LOOP.**
  - The bug's symptom (a hang that also eats memory) consumed 181 to 209 s of every run that reproduced it.
  - Both runs that edited "fixed" it by raising (`ValueError`, p4 in text.py, v7d in containers.py). That is a WRONG_SEMANTICS reading of "fix infinite loop": the test needs self-append to work.
  - Both runs also needed the sibling site (`append_text`), which no run reached.
  - This agrees with the old diagnosis (HANG, "fix the sibling site").
  - New measurements: the memory growth (1.6 GB in 4 s), and that 2 of 2 editing runs chose to raise.
- **Feasible in 5 minutes: maybe.**
  - Location takes 25 s in every run, the fix is 2 tokens at 2 sites, and the test takes 0.6 s.
  - The time lost to hangs is what removes it. Under v13's 60 s per-command limit each hang would cost 60 s instead of 181 s (inferred, not run).
  - 0 of 12 L4 runs and 0 of 6 box runs solved it, so the semantic risk (raising) stays.

## SOLVE

- **Lever:** `submissions/v13_repro_timeout`, which is v13 plus one appended prompt rule.
  - Every command that runs repository code outside a test file starts with `timeout 10`.
  - Exit code 124 means the code was still running after 10 s. When the issue is a hang or an infinite loop, that is the bug reproduced: read the loop it is stuck in and fix that, and do not rerun it with variations.
  - The rule has no code fence and no tool-call-like syntax (the v13 box regression warning of 2026-10-14).
- **Why this task, and the expected effect.**
  - Every hung repro here ran 181 s under v12 and would run 60 s under v13. With the rule it runs 10 s.
  - That gives b1024's trajectory back about 190 s against v12, or about 100 s against v13: two hangs at 50 s each, inferred.
  - The rule also tells the model that a hang is the reproduction. v7 and v7c spent their remaining turns trying to observe the loop.
  - It does not address the raise-versus-work choice or the sibling site. v13 already has the sibling rule.
- **Offline evidence (measured).**
  - 0 of 2,208 finished repro commands in the six box runs took over 2.0 s apart from the two self-cut at 5 s, so `timeout 10` would not have cut any legitimate repro.
  - The 13 hangs would each have cost 10 s instead of 180 s.
  - `tests/test_v13_repro_timeout.py` (6 tests, green) checks four things:
    - the bundle differs from v13 only by the appended rule line;
    - the line has no fence, tool syntax or braces;
    - `timeout 1 python3 -c 'while True: pass'` exits 124 and a `timeout 10 python3 - <<'EOF'` heredoc still runs;
    - the leakage check and `scripts/validate.py` pass.
- **Outside the 42:** rich_3882, solved by all six box runs. p4_v7c's `Prompt` repro waited on input for 180 s and the run still solved it at 252 s; with the rule that wait is 10 s. fastapi_14258 (in the 42) had 4 such hangs.
