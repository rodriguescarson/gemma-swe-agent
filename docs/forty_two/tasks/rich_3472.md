## Problem

- The issue is a maintainer PR titled "fix for missing field in dataclass" whose whole body is "Fixes https://github.com/Textualize/rich/issues/3417". It names no file, function, error text or example, and the sandbox cannot open the link.
- Bug: `rich.pretty` walks `fields(obj)` of a dataclass and calls `getattr(obj, field.name)` for each. A field declared with `field(init=False)` and no default is never set, so printing such an object raises `AttributeError` from `rich/pretty.py`.
- Gold: `rich/pretty.py`, 1 hunk, +3/-1. The field filter becomes `if field.repr and hasattr(obj, field.name)`: unset fields are left out of the repr.
- FAIL_TO_PASS (1): `tests/test_pretty.py::test_dataclass_no_attribute`. It prints a dataclass with one `init=False` field that was never set and asserts the output is exactly `BadDataclass()\n`.
- PASS_TO_PASS: 50 tests in `tests/test_pretty.py` (1 skipped). One of them, `test_pretty_dataclass`, pins that `repr=False` fields stay hidden.

## Root cause

- **Taxonomy: UNDERSPECIFIED_ISSUE -> WRONG_LOCATION** on the thinking-on line (b1024, v0-think: the title was read as a defect in one of the repository's own dataclasses, and every call went to `@dataclass` definitions). The thinking-off pipelines located the right file but failed on **WRONG_SEMANTICS** (v7 family: "missing" read as hidden `repr=False` fields) or a narrow **HIDDEN_SPEC** (p4: a placeholder value instead of leaving the field out).
- **Feasible in 5 minutes: maybe.** For: the gold is 1 line; a user program from the title names the file in one call (measured); a skip-on-`AttributeError` fix passes 51/51 (measured, below); the test costs 0.3 s. Against: 0 of 6 box runs and 0 of 12 L4 runs; the reading (b) is just as natural to the model and breaks a P2P test; a placeholder would still fail.
- **General levers** (no task content):
  1. **Title-only issue: locate by running a user's few lines, not by grepping the title's words.** When the issue has no identifier, error text or example, the title says what the library does wrong with some input; build that input, pass it to the library's usual public call, and take the file from the traceback or from the code that produced the wrong result. Here it turns 40 calls of `@dataclass` hunting into one call that names `rich/pretty.py:786`. Built as `submissions/v13_title_repro` (below).
  2. **Do not invent output the issue does not specify.** When a value is missing, leave it out or keep the existing behaviour rather than printing a new placeholder (p4's `'MISSING'`). Not built (one lever per bundle; this one only matters once the file is found).
  3. **Fail-first repro** (already in the rich dossiers): p4's verifier never got a crash repro running, so `pytest tests/test_pretty.py` passing was taken as evidence.
