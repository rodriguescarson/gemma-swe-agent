# rich_4006: infinite loop in `split_graphemes`

Sources. Measured numbers come from `docs/forty_two/ground_truth/rich_4006.json`, produced by `gt_rich.py` and `trace_rich.py` in
`docs/forty_two/ground_truth/rich_tools/`. Every pytest run went through `scripts/forty_two/bounded.py --mb 1500`, with 120 s per file

## Problem

- The issue is a maintainer PR: "fix for infinite loop in split_graphemes / Fix for https://github.com/Textualize/rich/issues/3958". That is all it says.
- Bug: the `while index < codepoint_count` loop in `rich/cells.split_graphemes` has three branches that can `continue` without advancing `index`, or without recording the character:
  - A zero-width character with no span before it (for example `"\x1b"` first). The `elif spans:` branch is skipped and `index` never moves, so it hangs.
  - A variation selector 16 (`"️"`) with no measured character before it. The `elif last_measured_character:` branch is skipped, so it hangs.
  - A zero-width joiner (`"‍"`) first or last. It does not hang, but it is dropped from the spans. At the end, `index += 2` overshoots: `"a‍"` gives the span `(0, 3, 1)`.
- Gold: `rich/cells.py`, 2 hunks, +33/-12. Every branch now advances, and a character with no previous span becomes its own 0-width span, so the spans cover every index.
- FAIL_TO_PASS (10):
  - `tests/test_cells.py::test_chop_cells_zero_width[...]` with 1 to 4 escapes (expects `[]`). These hang at base.
  - `test_split_graphemes` cases `"\x1b"`, `"\x1b\x1b"`, `"️"` and `"️️"`. These hang at base and expect spans such as `[(0, 1, 0)]` or `[(0, 2, 0)]` with width 0.
  - `test_split_graphemes` cases `"‍"` and `"‍‍"`. At base these return `[]` where `[(0, 1, 0)]` / `[(0, 2, 0)]` is expected.
- PASS_TO_PASS: 57 tests in `tests/test_cells.py`.

## Root cause

- **Taxonomy: HANG_INFINITE_LOOP with WRONG_SEMANTICS (partial).** Three branches fail to advance or to record a character.
  - The two runs that diagnosed quickly (p4, v7c) fixed one branch and stopped.
  - The two that probed the other hang lost 180 s to it (v7d, b1024).
  - The spans must cover every index, an invariant the existing expectations show. The old diagnosis (HANG, maybe) stands.
  - New measurements: the 3-branch structure, the 13-input sweep, and that every submitted patch still left a hang.
- **Feasible in 5 minutes: maybe.** Measured: location takes 13 s, a test takes 0.3 s, a sweep takes at most about 130 s and in practice 30 s. But the fix touches three branches and must emit 0-width spans. 0 of 12 L4 and 0 of 6 box runs solved it.

## SOLVE

- **Lever:** `submissions/v13_edge_sweep` (commit 9551169b), which is v13 plus one appended rule.
  - When the fix is inside a loop that walks over its input, call the fixed function before submitting on the edge inputs: empty, the special item alone, first, last and repeated. Run each in its own command under `timeout 10`.
  - Every call must finish, with output shaped like the existing test expectations (every position accounted for). Fix each failing case before submitting.
  - The rule has no code fence and no tool-call-like syntax.
- **Why here.**
  - p4 and v7c had about 250 s left when they submitted. The sweep shows them 3 remaining hangs and 2 uncovered indices within about 40 s (measured above).
  - v7d is in the same position with the mirror-image patch.
  - v13's 60 s per-command limit, already in the base, cuts the 180 s probe hangs of v7d and b1024 to 60 s. That is not part of this lever.
- **Tests:** `tests/test_v13_edge_sweep.py`, 5 tests, green. They check:
  - the bundle differs from v13 only by the appended line;
  - the line has no fence, tool syntax or braces;
  - the leakage check passes;
  - `scripts/validate.py` passes.
- **Outside the 42:** rich_3521 and rich_3506 (contested, `cell_len` off by 1-2 in failing runs, per the old diagnosis). A sweep over empty, first, last and wide-character inputs is the check those runs skipped (inferred). Inside the 42, rich_3953 (`cells.py`, control-character edge cases) is the same shape.
- **Queue:** `docs/forty_two/queue/rich_4006.json`.
