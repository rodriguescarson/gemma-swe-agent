# rich_3675: Implement the TTY_COMPATIBLE environment variable

Sources. Measured numbers come from `docs/forty_two/ground_truth/rich_3675.json` (`gt_rich.py` and `trace_rich.py` in
`docs/forty_two/ground_truth/rich_tools/`). Box rows are in `eval/a6000/results/<run>/results.jsonl` and L4 rows in
`eval/kaggle/<run>/results.jsonl`. "Inferred" marks claims no command checked.

## Problem

- The issue is a maintainer PR: "TTY_COMPATIBLE / Implement new `TTY_COMPATIBLE` environment variable", three @-mentions, and "Relevant discussion: https://github.com/Textualize/rich/issues/2924". That is the whole text.
- Gold touches `rich/console.py` and `rich/diagnose.py` in 5 hunks, +28/-13. The part that matters is in `Console.is_terminal`, before the `isatty()` auto-detect:
  - `TTY_COMPATIBLE == "0"` returns False.
  - `TTY_COMPATIBLE == "1"` returns True.
  - Any other value, including empty, falls through.
  - Gold also changes `FORCE_COLOR` (empty means not a terminal, and it no longer sets `_force_terminal`) and `NO_COLOR` (empty means unset). It reorders `diagnose` and touches comments and docstrings.
- FAIL_TO_PASS (1): `tests/test_console.py::test_tty_compatible`, using `FakeFile` and `FakeTTY` objects that record whether `isatty()` was called:
  - Default: auto-detect.
  - `"1"`: terminal **without** calling `isatty`.
  - `""` and `"whatever"`: auto-detect (must call `isatty`).
  - `"0"` on a TTY: not a terminal, without calling `isatty`.
- PASS_TO_PASS: 98 tests in `tests/test_console.py` (the test patch also adds `-> None` annotations).

  - This is a hidden spec, but a guessable one: "COMPATIBLE" reads as a boolean flag, and 2 L4 runs guessed `0`/`1`.

- **Test cost (indicative, clean Mac):**

  - Full suite: 4.15 s, with 3 failures outside the target file: `test_markdown::test_inline_code` and 2 in `test_syntax`, which are Pygments 2.20 colouring. They fail at base too (measured). The target file is clean.

## Kaggle L4 runs

2 of the 12 74-row L4 runs resolved it: g4-l4-v4 (13 calls, 64 s) and g4-l4-v9-eog (10 calls, 47 s).
- Both inserted `if tty_compatible == "1": return True` / `if tty_compatible == "0": return False` **after** the unchanged `FORCE_COLOR` block.
- So the gold's `FORCE_COLOR`/`NO_COLOR` changes are not needed for the test (Kaggle-verified). This corrects the old diagnosis, which said the test fails "because the gold also changes FORCE_COLOR semantics".
- The other 10 L4 runs failed in 42 to 157 s, except v5h2-think, which ran 306 s. Inferred: they wrote the same "any value" patch.

## Root cause

- **Taxonomy: HIDDEN_SPEC, value semantics.** The `0`/`1`/fall-through contract is only in the linked discussion and the test.
  - All six box runs (temperatures 0.2 and 1.0, four prompt families) converged on the one template the file offers: the "any value" `FORCE_COLOR` block.
  - Correction to the old diagnosis: the hidden part is smaller than it said. Only the env-value contract is hidden, not a `FORCE_COLOR` rewrite.
- **Feasible in 5 minutes: maybe.** Measured: 2 of 12 L4 runs guessed it in under 65 s, and a test run costs 0.5 s. The guess is the whole difficulty.
- **General lever** (a convention, not this task's answer):
  - **Prompt rule for new env vars and flags.** Give explicit values (`1`/`true` on, `0`/`false` off) their meaning. Make every other value, **including empty**, keep today's behaviour.
  - **Repro rule.** The repro must assert the unset, empty and unknown-value cases unchanged, not only the new "on" value. Every box run tested only `"1"`.
  - This is the same "do not change behaviour for values the issue did not name" rule that applies to any option or parameter.
  - It is not proven to transfer; adding it to one bundle and measuring is the test.
