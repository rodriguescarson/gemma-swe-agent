## Problem

- The issue is a maintainer PR, "Fix traceback recursion". It contains only two links: "Fixes ...rich/issues/3708" and "Fixes .../3682".
- Bug: `Traceback.extract` walks `__cause__` / `__context__` in a `while True` loop, and recurses into `ExceptionGroup` members, with no record of what it has already visited. An exception that is its own cause (`raise e from e`), or a group that contains an exception it already saw, makes it loop forever and build stacks without bound.
- Gold (`rich/traceback.py`, 6 hunks, +29/-16):
  - threads a `_visited_exceptions` set through `extract`;
  - skips group members it has already seen;
  - follows `__cause__` / `__context__` only when no group was walked and `cause is not exc_value`.
- FAIL_TO_PASS (1): `tests/test_traceback.py::test_recursive_exception`. Inside `foo()`, `raise e from e`. `bar()` catches it, asserts `e is e.__cause__`, and calls `console.print_exception(show_locals=True)`, which must return.
- PASS_TO_PASS: 21 tests, plus 1 skipped.

## Root cause

- **Taxonomy: UNDERSPECIFIED_ISSUE leading to WRONG_LOCATION.** "Recursion" was read as the excepthook recursing, and the edits went into `install()`, not `extract`. The bug's symptom then made every wrong patch hang in verification (HANG_INFINITE_LOOP).
  - The deciding failure: **no failing repro before editing** in five of five failing runs. v7c's `RecursionError` repro did not fail at base (measured), and the run still edited.
  - The old diagnosis (HANG, maybe; "v4 edited install(), v8 extract without a visited set") is consistent. New: v0-think's success, and the measurement that deep recursion is not the bug.
- **Feasible in 5 minutes: maybe.** Measured: v0-think solved it on the box in 293 s with 7 s to spare. The fix is a few lines and the target test takes 0.6 s. But 0 of 12 L4 runs and 5 of 6 box runs solved it.

## SOLVE

- **Lever: reuse `submissions/v13_redfirst`**, built by the fastapi agent on `origin/forty-two-fastapi-solve` (commit 02d63d09). It is v13 plus one sentence group at the end of step 2:
  - before the first edit, run the issue's example as a heredoc that asserts the result the issue asks for, plus one ordinary input;
  - the first assert must fail now, and if it passes, the example misses the bug, so change it;
  - rerun the same check after each edit until both asserts pass.
- **Why this lever flips this task (measured, `edge_sweep`).** The failing runs' own notion of the bug, deep recursion, passes at base. Under this rule that check is green before any edit, which the rule names as "the example misses the bug". The model must then look for an input that fails, and the only failing one is the cycle (`raise e from e`), which hangs. All five failing patches fail that check (still hang) and gold passes it, so none of them could have been submitted with a green check.
  - The check must run bounded, and v13's 60 s per-command limit is in the base. `v13_repro_timeout` (rich_3480) would cut a hanging check to 10 s and name exit 124 as "reproduced". That is a separate lever, not stacked here.
- **Tests and validation** are the fastapi agent's (`tests/test_v13_fastapi_levers.py` on that branch); not re-run here.
- **Outside the 42:** fastapi_14458, resolved at the cap after three green checks and no red one (from the fastapi queue file); rich_3894 (contested, no run executed a test).
