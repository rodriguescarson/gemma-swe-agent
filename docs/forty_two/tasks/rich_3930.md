## Problem

- The issue is a maintainer PR titled "Handle graphemes" (1,224 characters). It explains that rich now follows Unicode rules for multi-codepoint emoji, uses wcwidth's data (not the package), adds the ability to split strings into single-glyph sequences, and stores the data so start-up stays fast. "Fixes #3897".
- Gold: 29 hunks, +12,170/-544. It deletes `rich/_cell_widths.py` (454 lines), adds a package `rich/_unicode_data/` (an `__init__.py` with `load`, `VERSIONS`, `_parse_version`, a `_versions.py`, and 21 generated tables `unicode4-1-0.py` ... `unicode17-0-0.py`, 425-691 lines each), and rewrites `rich/cells.py` (+239/-88: `CellSpan`, `split_graphemes`, `split_text`, a versioned `get_character_cell_size`).
- Tests: `tests/test_cells.py`, `tests/test_text.py`, and a new `tests/test_unicode_data.py`. Before the gold patch, `test_cells.py` and `test_unicode_data.py` fail to import (`from rich.cells import CellSpan, ... split_graphemes, split_text`; `from rich._unicode_data import VERSIONS, _parse_version, load`), the collection errors abort the session ("2 errors"), and so every test in the three files counts as FAIL_TO_PASS: **189 F2P, 0 P2P**.
- The F2P tests pin exact behaviour: span tuples per grapheme (`("👩‍🔧", [(0, 3, 2)], 2)`), `split_text` at every offset of mixed-width strings (a split inside a double-width glyph yields two spaces), `load_version("4.0.2") == "4.1.0"`, `_parse_version("1.2") == (1, 2, 0)`.
