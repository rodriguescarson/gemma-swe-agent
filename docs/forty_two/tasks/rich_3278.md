# rich_3278: Strip private escape sequences (`\x1b0` to `\x1b?`)

Sources. Measured numbers come from `docs/forty_two/ground_truth/rich_3278.json` (`gt_rich.py` and `trace_rich.py` in
`docs/forty_two/ground_truth/rich_tools/`). Box rows are in `eval/a6000/results/<run>/results.jsonl` and L4 rows in
`eval/kaggle/<run>/results.jsonl`. "Inferred" marks claims no command checked.

## Problem

- The issue is a contributor PR, "Strip problematic private escape sequences".
  - It says the ANSI parser should ignore the `\x1b0` to `\x1b?` escape sequences.
  - It notes that `\x1b7` and `\x1b8` (save and restore cursor) are common, and that printing them "causes havoc".
- Gold: `rich/ansi.py`, 1 hunk, +1/-0. One alternative is added at the top of the raw, verbose `re_ansi` pattern: `(?:\x1b[0-?])|`.
- FAIL_TO_PASS (16): `tests/test_ansi.py::test_strip_private_escape_sequences[0..9 : ; < = > ?]`. For each character `c`, `Text.from_ansi(f"\x1b{c}x")` printed through a terminal console must capture exactly `"x\n"`.
- PASS_TO_PASS: 7 existing tests in `tests/test_ansi.py`, including `test_decode` and `test_decode_example`. They pin the CSI (`\x1b[...m`) parsing that any regex edit must keep.

## Constraints

- **Budget.** v12-b1024 and v0-think: 5 min, 40 calls, 180 s per command. v5h2 and v7*: 5 min, 70 calls, 180 s.
- **What the issue gives:**
  - The exact byte range (`\x1b0`-`\x1b?`, which is the regex class `[0-?]`) and the component ("the ANSI parser"). `rich/ansi.py` is the only file with `re_ansi`.
  - Nothing is hidden. The difficulty is purely mechanical: the pattern is a **raw** triple-quoted string. The file must contain one backslash in `\x1b`, and two backslashes in the existing `\\-` that escape a literal backslash. Every tool layer (JSON arguments, heredoc, `edit_file`) invites doubling them.
- **Gold in a clean environment: passes** (23 passed). The result is the same with Pygments 2.21.0 and with `ipython_pygments_lexers`.
- **Test cost (indicative, clean Mac):**
  - `tests/test_ansi.py`: 0.30 s.
  - F2P only: 0.28 s.
  - Install: 0.54 s.
  - Full suite: 4.98 s, but **55 failures already exist at this base commit**, measured. They come from 13 files (test_table 16, test_inspect 15, test_markdown 5, ...). One is `Column.__init__() got an unexpected keyword argument 'highlight'` in `rich/table.py`. An agent running the whole suite would see 55 unrelated failures.
  - In the box, the helper `test.py --target tests/test_ansi.py` took about 0.2 s per call (traces).

## Root cause

- **Taxonomy: EDIT_TOOL_FAILURE, escape layering.** The fix is one line and fully specified. The runs could not write a single backslash into a raw regex through JSON plus heredoc (v5h2, v7*), or were paralysed by doubt about it (b1024). The one run that wrote it correctly (v0-think) then made a WRONG_SEMANTICS character-class error that a 0.3 s test run would have caught.
  - The old diagnosis said "67-96 FileEditError, escaped `\x1b`". That is corrected for these runs: there were 0 FileEditErrors. The edits **succeeded** with doubled backslashes, then looped as no-ops.
- **Feasible in 5 minutes: yes.** Measured: the gold is a 1-line insertion, the target test takes 0.3 s, and 2 of 12 L4 runs solved it in 98 and 283 s.
- **General levers:**
  1. **Escape-drift check in the edit path.** After any edit, compare the backslash runs of the replaced and replacement text. If `\x`, `\[` or `\d` became `\\x`, `\\[` or `\\d`, report "your replacement doubled backslashes; the file had one". It applies to any regex or escape string in any repo. A helper script or a prompt rule (`git diff` and count backslashes) can do it.
  2. **Regression gate.** If a test that passed before the edit now fails (here `test_decode`, which the p4 verifier saw at 58 s), revert and redo the edit, rather than resending it. Combined with a refusal of identical no-op edits ("NO CHANGE" twice means stop), this would have saved about 100 s in p4.
  3. **Run the edited module's test file once before submitting.** For v0-think that is 0.3 s and would show 3 regressions.
  4. **Cap thinking per turn / experiments per hypothesis.** b1024 spent 246 s on 9 inline re-implementations instead of editing and running the real test. A rule such as "after 2 experiments, edit and run the module's tests" applies anywhere.
