## Problem

- The issue is a contributor PR, "Case insensitive prompt choices". It adds an optional flag, `Prompt.ask(..., choices=["Paul", "Jessica", "Duncan"], default="Paul", case_sensitive=False)`, so that "it would accept 'paul' or 'Paul' as valid responses". The default is True.
- Gold changes `rich/prompt.py` in 12 hunks, +29/-5:
  - it threads `case_sensitive` through `PromptBase.__init__`, both `ask` overloads and the `ask` body;
  - it compares lowercased values in the choice check;
  - in `process_response` it **returns the declared choice**, `self.choices[...index(value.lower())]`, not the typed text.
- FAIL_TO_PASS (1): `tests/test_prompt.py::test_prompt_str_case_insensitive`. With input `"egg\nFoO"` and `choices=["foo", "bar"]`, the test asserts two things:
  - the first line is rejected ("Please select one of the available options");
  - `name == "foo"`, which is the declared choice, not `"FoO"`.
- PASS_TO_PASS: 6 tests in `tests/test_prompt.py`.

## Root cause

- **Taxonomy: WRONG_SEMANTICS (return contract).** The new looser match is implemented, but the call returns the raw input instead of the declared choice.
  - The old diagnosis said EDIT_TOOL_FAILURE (125 to 142 malformed calls), which is **corrected for the current runs**:
    - 0 malformed calls in all seven runs;
    - five runs, including v13 with the edit template, produced the same wrong-semantics patch.
  - The edit failures that remain are a v5h2 self-revert and v7d's corrupting replacement.
- **Feasible in 5 minutes: yes.** Measured: a one-line membership assert on the issue's example exposes the bug on all five patches. The fix is a few lines in one function, and five runs submitted with 60 to 170 s to spare.

## SOLVE

- **Lever:** `submissions/v13_keep_contract` (commit 49d7c777), which is v13 plus one appended rule. When a change makes a function accept new inputs (looser matching, a new option, a new argument type), the check must also assert what the function returns for those inputs:
  - the same type as before;
  - when the caller passes a set of allowed values, one of those values exactly as declared, not the raw input.
  - The rule has no code fence and no tool-call-like syntax.
- **Offline evidence (measured):** the edge sweep above. The assert this rule asks for fails on 5 of 5 submitted patches and passes on gold.
- **Tests:** `tests/test_v13_keep_contract.py`, 5 tests, green. They check:
  - the bundle differs from v13 only by the appended line;
  - the line has no fence, tool syntax or braces;
  - the leakage check passes;
  - `scripts/validate.py` passes.
- **Outside the 42:** any normalising option, for example case-insensitive enum or CLI-choice matching, where a caller compares the result to its declared values. In this repository's public set: fastapi_14616 (in the 42) and fastapi_9425 (contested; a 204 response that must keep returning no body). The same "accepts more, must still return the same shape" check applies there (inferred). Another agent's `v13_redfirst` (a fail-first assert of the issue's result) is close, but it does not name the return contract. All five runs here wrote an "accepted" assert that passed.
