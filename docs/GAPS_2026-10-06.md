# Gaps in the approach (find-gaps session, 2026-10-06)

Evidence used: docs/v4h/GATE.md, docs/v11/PLAN.md, the plan file (Phase 2A/2B), L4 results in eval/kaggle/.
Key numbers: best single L4 run 34/74; union of 6 L4 runs 41/74 (+7 from run-to-run variance alone); median task
time 124-163 s of a 300 s cap (about half the budget unused); hidden reads 3-6/58 for every recent bundle; Pallets
off-repo 29/97 (v4h2 = v5h2), 20/97 (v4h2g).

## Blockers
B1. Success metric. The goal says 74/74 public; the competition pays on ~120 hidden tasks from other repos, and
    public-74 gains (+9) did not transfer (hidden -1..+2). ~22 public tasks are unsolvable from their text. Decision
    needed: which number do we optimise and report?
B2. No test-time scaling. Plan Phase 2A (ParallelAgent K candidates + test-based selection) was never built, though
    pass@6 = 41 vs pass@1 = 34 and half of each task's 5 minutes is unused. Candidate generation + a selector
    (run the repro / targeted tests, pick the passing diff) is the largest unused lever.
B3. No faithful, high-throughput evaluator or budget. Kaggle L4: ~4 runs/week (2x billing); OpenRouter proxy: fp8,
    different tool parser, ~4x slower so 30-43 of 57 tasks hit the cap, $6 left. Every decision rests on n<=97
    single-sample comparisons. A6000 setup pending; no spend cap set.

## Should-address
S1. Statistics: no power analysis. With ~30% solve rate a 97-task paired comparison only detects ~8+ task gaps;
    no A/A noise run on the proxy; one sample per task per arm.
S2. LoRA method and data: v11a/b came from 49 solved tasks; no rejection-sampling fine-tuning (RFT/STaR) at scale on
    the 1,044 new tasks, no preference training (DPO on solved vs failed trajectories of the same task), no
    curriculum; adapters never shown to help on an off-repo set.
S3. Wrong-fix is the largest addressable miss class (~29 of 40 misses edit the right file wrongly) but nothing
    targets it directly: no reproduction-test generation before the edit, no "run the repro and the nearby tests,
    retry if red" loop with a hard rule.
S4. Thinking: only tested at large budgets (too slow). thinking_budget is not forwarded; thinking_level LOW on the
    fixer only (where the reasoning matters) was never tried.
S5. Time budget: hidden 12 h / ~120 tasks = 6 min incl. setup; we cap at 5 min and use ~2.3. The cap is not the
    binding constraint; the 70-call cap and loops are.
S6. Shell-command repetition loops (16 misses) have no structural fix; only prompts, which the model ignores.

## Nice-to-have
N1. Retrieval quality on off-repo tasks not measured (file recall@k of locate.py vs gold files on heldout1k).
N2. Graph/embedding tools unused (the shipped graphs were broken; the hidden set's may not be).
N3. Paper track ($35k, Nov 12) not started; team merge (Nov 25) not explored.
N4. Learn from the leader (0.24): no code public; forum methods not mined since 10-05.

## Decisions (filled in below as each gap is closed)
- B1 (Carson, 2026-10-06): the target stays **74/74 on the public tasks, as written**. A change is kept when it raises
  the public-74 solved count on a faithful Kaggle L4 run. Trade-off recorded: public gains have not transferred to the
  hidden split (+9 public -> -1..+2 hidden) and ~22 public tasks are unsolvable from their text, so the off-repo
  held-out set and hidden reads are tracked alongside as a check, not as the decision rule.
- B2 (Carson, 2026-10-06): build best-of-3 with test-based selection.
  AC-B2 (bundle v6p, base v5h2): pipeline setup -> locator -> ParallelAgent[fixer_a T0.2, fixer_b T0.6,
  fixer_c T0.9] -> selector -> verifier. Each fixer copies /workspace to /tmp/wK first, edits only there, and ends
  with /tmp/wK.diff. Selector = deterministic skill script select.py: apply each diff to a clean copy, run the repro
  (/tmp/repro.py if present) + the locator's TEST file; pick the diff passing the most, ties -> smallest diff; none
  pass -> the non-empty diff with the most passes; all empty -> leave /workspace unchanged; apply the pick to
  /workspace (git checkout first). Pass (one faithful L4 run, public 74): solved >= 37 (v4h2g 34 + 3), helper gate
  passes, median task secs <= 240, projected 120-task wall clock <= 10 h. Fail -> no slot; read traces.
- B3 (Carson, 2026-10-06): free compute only. Kaggle L4 (~4 faithful 74-task runs a week, 2x quota billing) is the
  deciding run; the friend's A6000 screens candidates for free once connected (scripts/a6000/FRIEND_SETUP.md). No
  rented GPUs; OpenRouter only from the remaining $6.28.
- Queue (Carson, 2026-10-06): once v6p passes its tests, the L4 queue becomes v6p -> v5h2 (single-attempt control for
  attribution); v5h2b and the v11b adapter probe wait for the A6000. Requeue happens when the v6p kernel exists
  (the weekly quota is not free before Saturday, so nothing is lost by waiting).
- S1 keep rule (Carson, 2026-10-06): a candidate is kept when, on one faithful L4 run of the public 74, it solves
  >= 37 AND, paired task-by-task against v4h2g's L4 run (eval/kaggle/g4-l4-v4h2g-p312/results.jsonl), its wins minus
  losses >= +3. Reason: the same bundle moves ~2-3 tasks between L4 runs (v4 29 vs 27), so the raw total alone
  passes a lucky +3 about 1 time in 4. AC-B2's pass condition uses this rule.
- S2 LoRA (Carson, 2026-10-06): next adapter = self-generated data on the held-out set plus preference pairs. On the
  A6000, Gemma attempts the 1,044 held-out tasks several times each (same bundle, faithful budgets). Test-verified
  successes -> SFT rows (rejection sampling); for tasks with both a solved and a failed attempt -> (chosen, rejected)
  pairs. Train on Adaption: SFT (training_method "instruction"), then preference training (SDK 0.13.0 accepts
  training_method "alignment" on preference pairs, i.e. DPO). No closed-model data. Kept only under the S1 keep rule
  on L4 public 74. Blocked on the A6000.
- S3 wrong-fix (Carson, 2026-10-06): the locator writes /tmp/repro.py from the issue's example (bare asserts, exits
  non-zero on failure) and runs it on the unedited code; it must FAIL there (if it passes, the locator rewrites it
  once, else notes "REPRO: none"). The plan carries "REPRO: /tmp/repro.py (fails before fix)". All three fixers must
  make it pass in their copy; select.py ranks candidates on repro first, then the TEST file. Applies to v6p (AC-B2).
- S4 thinking (Carson, 2026-10-06): thinking_level LOW on the fixers only is screened on the A6000 against v6p on
  heldout1k/harness_s200 (free). It reaches an L4 run only if it beats v6p there and keeps median task secs <= 240.
  Not mixed into v6p's first L4 run.
- S5 time cap (Carson, 2026-10-06): v6p runs at 5 min per task. Raise to 5.5 min only if its L4 run shows > 10 tasks
  hitting the cap AND a projected 120-task wall clock < 10 h (12 h overrun errors the whole submission).
- S6 loops (Carson, 2026-10-06): contained by best-of-3. Each fixer prompt carries a hard call cap (~15); a looping
  attempt burns only its own share; select.py ignores empty diffs. v6p's L4 traces are measured for loops (same
  identical call >= 5 in a row) per stage before anything further is built.
- Nice-to-haves (Carson, 2026-10-06): all four on the list.
  N1 locate recall on heldout1k (free, local, now). N3 paper track, deadline 2026-11-12 23:59 UTC (Carson to join the
  track on Kaggle; draft from GATE.md evidence). N4 forum/leader scan for methods >= 0.15 since 2026-10-05 (free,
  now). N2 graph tools re-test: needs a model run, so on the A6000 after v6p.
